# Tests

Node's built-in test runner, no test framework. From the repository root:

    npm test                                                   # everything (about 45 s; builds the P0JBVA rasters first if they are missing)
    npm run fixtures                                           # rebuild the P0JBVA rasters (about 8 s)
    node --test --test-reporter=spec tests/mesh/performance.test.mjs   # timings against the phase 1 budgets

`.github/workflows/test.yaml` runs `npm test` on every push and pull request; `release-on-tag.yaml` runs it again before a release is drafted.

- `tutorial/`: the wiki's tutorial pages, played in the web studio (see [The tutorial](#the-tutorial-tutorial) below).
- `support/`: shared helpers that are not tests. `pipeline-setup.mjs` builds a stand-in for the studio app from a saved map so the generation pipeline can run outside Foundry; `web-worker-shim.mjs` gives Node a browser-style module `Worker`.

Two checks run the studio in headless Chromium (Playwright) and stay in `design/`, run by hand: `design/prototypes/thin-frame/studio-smoke-check.mjs` (the studio in a stand-in Foundry window) and `design/prototypes/web/web-smoke-check.mjs` (the web version, from the working copy or any site address). The browser render check for the region fill (`design/tests/mesh/browser/render-check.mjs`, headless Chromium through Playwright) stays in `design/` and is run by hand; it reads the fixtures from here.

## The tutorial (`tutorial/`)

The wiki's tutorial is written as step files, one per page (`tutorial/pages/<nn>-<slug>.mjs`), and played in the web studio by a runner (`tutorial/run.mjs`, Playwright with Chromium and SwiftShader, at 1,600 × 1,000 in dark teal). Each step works the studio as a reader does, through its controls and the map, and the run fails naming the step when one cannot be done (a control missing or covered, a map point under an overlay, a check on the studio's state that does not hold).

    npm run tutorial:build             # play every page; write its screenshots, checkpoint, wiki page and video script
    npm run tutorial:build -- 1 3      # only pages 1 and 3
    npm run tutorial:texts             # only the wiki pages and video scripts, without a browser
    node --test tests/tutorial/tutorial.test.mjs   # play every page and write nothing (part of npm test)

What a build writes:

- `wiki/images/tutorial/<nn>-<slug>-<shot>.png`: the step screenshots, in the wiki's own repository.
- `samples/tutorial/<nn>-<slug>.json`: the map at the end of the page, exported through **Maps**, which the next page starts from (imported through **Import JSON**, as the page tells the reader). Tracked: the check starts each page from it.
- `wiki/Tutorial-<nn>-<Title>.md`: the wiki page, with a note that it is generated.
- `tutorial/scripts/<nn>-<slug>.md`: the video's shooting script: per step, the narration, what happens on screen, the camera and how long to hold.

The wiki pages and scripts are written for every page, not only those played, since a page's text depends on its neighbours (its Start from and Next links, and the page count).

The wiki's other screenshots come from the same harness. Each wiki page marks where a picture goes with a comment, `<!-- screenshot: <slug> | <what it shows> -->`, and has a shots file (`tutorial/shots/<Wiki-page>.mjs`) saying, for each comment, which tutorial checkpoint it starts from, what to do in the studio and what to capture (`tutorial/shots/_common.mjs` holds what they share).

    npm run tutorial:shots             # every wiki page's screenshots
    npm run tutorial:shots -- Biomes   # only the Biomes page's

A run writes `wiki/images/<page>/<slug>.png` and puts the image and its caption under the comment in the wiki page (the comment stays, so a rerun replaces them). A shot marked `provided` is a picture from Foundry, which the harness cannot open, saved by hand at its path. `tutorial/shots.test.mjs` (part of `npm test`) checks that the comments and the shots files match, where the wiki is checked out.

Random numbers in the page are seeded (`lib/studio.mjs`), so a rebuild writes the same ids, the same checkpoint and, on the same Chromium, the same screenshots, byte for byte.

A step file exports its page: `number`, `slug`, `title`, `goal`, `start` (the page before's stem, or none for page 1), the wiki's `intro`, `whatYouSee`, `foundry` and `onYourOwn`, an opening `narration`, and the `steps`. A step has an `id`; the reader's `instruction` (Markdown; a step without one is done but not shown); its `action`, one or a list of `{ do, ...fields, label }` (`tool`, `mode`, `click`, `openSection`, `set`, `dialog`, `waitForDialog`, `mapClick`, `shape`, `camera`, `zoom`, `slide`, `drag`, `brush`, `key`, `hover`, `importMap`, `settle`, `expect`; see `lib/actions.mjs`); an optional `screenshot` (`name`, `region`: `studio`, `rail`, `panel`, `bar`, `map`, `inspector`, `dialog`, `{ selector }`, `{ map: [x0, y0, x1, y1] }` or `{ union }`, with `pad`, `pointer` and `mapOnly`), `caption` and `note`; and the video's `narration`, `pause` (seconds to hold) and `camera`. After every step the runner waits for the map to settle; `settle: false` skips that (a step that leaves a dialogue open).

The pages take a few minutes each, and up to twenty once the map is generated (SwiftShader draws thousands of names), so the check is slow: `FWMB_TUTORIAL=0 npm test` leaves it out. The pages play one at a time; `FWMB_TUTORIAL_CONCURRENCY=2` plays two at once on a machine with the cores for it. CI runs it in its own job, which installs Chromium; the main job has none, so the check skips there.

## Fixtures (`mesh/fixtures/`)

- `p0jbva.json`: the P0JBVA map (2000 × 1600, seed `P0JBVA`), the saved-map JSON the other fixtures are built from. It is the tutorial's map at the end of page 4, with the land finished (`samples/tutorial/04-rivers-and-faults.json`): `npm run tutorial:build` copies it here, and a check in `tutorial/tutorial.test.mjs` fails if the two differ. Change P0JBVA by changing the tutorial's pages 1 to 4, never by editing this file.
- `p0jbva/`: the map's terrain rasters (elevation, water mask, river map, moisture and temperature) and its traced rivers with their flow, **derived data that is not committed**: `build-p0jbva.mjs` regenerates them by running the module's own generation pipeline on `p0jbva.json`, so they always match the current engine. `npm test` builds them when they are missing or `p0jbva.json` has changed since (the rasters record the file they were built from); `npm run fixtures` rebuilds them after an engine change. Tests that need them skip, and say so, when they are absent.
- `v3-vectors.json`: `p0jbva.json` with hand-written v3 region layers (an overlapping pair, one around a lake, a tiny one), routes (two sharing a node, one repeating a node) and pins, for the migration tests.
- `p0jbva-realms.json`: the settlement prototype's final realms carried onto P0JBVA's display mesh (vote, fill, relax, sea claims), RLE encoded, with the mesh block they belong to. Rebuilt with `make-realm-layer.mjs` from a prototype run; only needed again if `MESH.ALGORITHM_VERSION` changes.
- `expected-sites.json`: hashes of the sampled sites, the cross-engine determinism check. If it fails after a deliberate sampler change, bump `MESH.ALGORITHM_VERSION`, regenerate this file and the realm fixture.

## Conventions

- Files are `*.test.mjs`; anything else under `tests/` is a helper or fixture and is not run.
- Tests must pass on a shared CI runner: the performance budgets are skipped where `CI` is set (set `FWMB_PERF` as well to run them there).
- A harness in `design/` that becomes a repeatable check moves here; a one-off investigation stays in `design/`.
